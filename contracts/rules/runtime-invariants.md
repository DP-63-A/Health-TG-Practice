# Правила owner / повторов / revision (вне JSON Schema)

Эти инварианты **не** проверяются схемами и примерами. Схемная валидация не выдаётся за их реализацию (AC4).

## Owner

1. Каждый HTTP-запрос (кроме `/healthz` и `POST /auth/telegram`) требует валидной сессии.
2. Entry, file и analytics доступны только владельцу (`user_id` сессии).
3. Политика чужого ID: см. OPEN-DECISIONS D3 (черновик: 404).

## Revision и конфликты

1. Каждая успешная мутация увеличивает `revision` на 1.
2. `PATCH` / `confirm` принимают `expected_revision` в теле; несовпадение → **409** `VERSION_CONFLICT`.
3. `DELETE` передаёт ту же версию через `If-Match` (см. D4).
4. Ответ 409 содержит актуальную карточку или достаточно данных, чтобы клиент перечитал запись.

## Идемпотентность

1. `POST .../confirm` с тем же `submission_id` возвращает тот же логический результат и **не** создаёт вторую confirmed-запись.
2. Повтор Telegram update защищается уникальным ключом на стороне ядра (BE1-03 / BE2), не публичным API.
3. `cancel` принимает текущую версию через `If-Match`, как и `delete`. Это не позволяет старой кнопке
   отменить draft после более новой правки. Повтор того же успешного cancel с исходной версией
   возвращает сохранённый cancelled-результат; другая устаревшая версия даёт 409.
4. Повтор `delete` на уже `deleted`: поведение согласовать отдельно; текущая реализация возвращает
   409 `INVALID_STATUS_TRANSITION`.

## Статусы (логика переходов)

| Из \ В | draft | confirmed | cancelled | deleted |
|---|---|---|---|---|
| draft | — | confirm | cancel | не через DELETE* |
| confirmed | нет | — | нет | DELETE (логическое) |
| cancelled | нет | нет | — | нет |
| deleted | нет | нет | нет | — |

\* Удаление черновика — через `cancel`, не через `DELETE` дневника.

- Только `confirmed` участвуют в аналитике и в `GET /entries` по умолчанию.
- `status=draft` — для экрана проверки; `cancelled`/`deleted` в список дневника не попадают.

## Null vs zero

- Неизвестное значение: JSON `null` (или отсутствие ключа только там, где схема допускает omit).
- Ноль — валидное измеренное/введённое значение (`0` шагов после уточнения допустим только если пользователь/источник явно сообщил 0; отрицательные шаги/длительность сна/пульс — **422**).
- Подтверждение (`confirm`) **не** меняет `field_origins.*.estimated` на «достоверное».
- Черновик `metrics` может не содержать `unit` и `local_date` либо содержать для них `null`, если распознавание не дало надёжного значения. Перед переходом в `confirmed` оба поля обязательны и не могут быть `null`.

## Питание и масса

- `nutrients_basis=per_100g`: значения `nutrients` относятся к 100 г. Итог порции равен значению, умноженному на `mass_g / 100`.
- `nutrients_basis=per_serving`: значения `nutrients` относятся ко всей сохранённой порции.
- `nutrients_basis=unknown`: автоматическое масштабирование запрещено до уточнения основы.
- При изменении `mass_g` для `per_100g` итог порции пересчитывается из неизменных значений на 100 г; нельзя повторно масштабировать уже рассчитанный итог.

## Границы календарного периода

- `list_confirmed_entries` принимает включительные календарные даты `from`/`to` и обязательный IANA `timezone` владельца.
- Для `steps`, `sleep_duration_min` и `heart_rate` включительный диапазон сравнивается с `payload.local_date`, без преобразования в UTC. Для остальных записей реальный диапазон времени является полуоткрытым: от начала `from` включительно до начала дня после `to` исключительно в переданном часовом поясе. UTC-границы вычисляются после применения timezone, включая переходы летнего времени.

## Дневные итоги шагов

- `payload.local_date` — день, за который сообщены шаги; `occurred_at` — полный момент исходного сообщения итога в UTC. В Telegram это `message.date`, а не время обработки или последующего уточнения даты.
- Дневник и аналитика отбирают и группируют шаги по `local_date`. Среди подтверждённых итогов за день выбирается последний по `occurred_at → updated_at → id`; значения повторных итогов не складываются.
- Пример: 4 октября в 20:00 сообщено 8 000, 5 октября в 09:00 — 9 000 за 4 октября. В расчёте за 4 октября остаётся 9 000; в расчёт за 5 октября эти записи не входят.
- Исправление дня меняет только `local_date`. PATCH другого `occurred_at` для шагов, сна и пульса отклоняется (422). Изменение кода метрики также отклоняется: он изменил бы смысл сохранённого времени; следует создать новую запись. Проверки владельца и revision сохраняются.
- Время ходьбы не требуется. `local_time` не участвует в выборе итога. Для сна `local_date` — дата пробуждения, для пульса — дата измерения. Их `occurred_at` также хранит неизменяемый момент исходного сообщения. Неизвестное время измерения остаётся неизвестным.
- Другой источник должен передать достоверный полный момент сообщения итога. Если он неизвестен, нельзя заменять его текущим временем. Публичного создания Entry из Mini App нет.
- Старые записи не мигрируются автоматически. При известном `local_date` используются этот день и сохранённый `occurred_at`; исходный порядок старых сообщений восстановить без источника нельзя. Уточнения, сохранённые без времени исходного сообщения, требуют повторного ввода и не получают фиктивный timestamp.
- Шаги с отсутствующим или некорректным `local_date` не попадают в выборку по периоду и аналитику. В дневнике без ограничения дат они остаются доступны для исправления. Подтверждение по-прежнему требует известной даты. Неизвестную дату запрещено выводить из `occurred_at`.

## Сон и пульс — согласованные правила #94

- Дневник и аналитика используют только `payload.local_date`: дату пробуждения для сна и дату измерения для пульса. Отсутствующую дату не выводят из `occurred_at`; без даты запись не участвует в выборке периода.
- Сон выбирается за каждый день по `occurred_at → updated_at → id`. Для карточки пульса сначала выбирается самая поздняя `local_date` периода, затем последнее сообщение по тому же порядку.
- Правка даты меняет только `local_date`; исходный `occurred_at` неизменяем. Известный `local_time` сохраняется, неизвестный не заменяется текущим временем. Старые данные автоматически не мигрируются.
- Значение каждой из трёх метрик должно быть неотрицательным; отрицательное число не означает отсутствие данных.
