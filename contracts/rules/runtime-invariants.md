# Правила owner / повторов / revision (вне JSON Schema)

Эти инварианты **не** проверяются схемами и примерами. Схемная валидация не выдаётся за их реализацию (AC4).

## Owner

1. Каждый HTTP-запрос (кроме `/healthz` и `POST /auth/telegram`) требует валидной сессии.
2. Entry, file и analytics доступны только владельцу (`user_id` сессии).
3. Политика чужого ID: см. OPEN-DECISIONS D3 (черновик: 404).

## Revision и конфликты

1. Каждая успешная мутация увеличивает `revision` на 1.
2. `PATCH` / `confirm` принимают `expected_revision` в теле; несовпадение → **409** `VERSION_CONFLICT`.
3. `DELETE` передаёт ту же версию через `If-Match` (см. D4).
4. Ответ 409 содержит актуальную карточку или достаточно данных, чтобы клиент перечитал запись.

## Идемпотентность

1. `POST .../confirm` с тем же `submission_id` возвращает тот же логический результат и **не** создаёт вторую confirmed-запись.
2. Повтор Telegram update защищается уникальным ключом на стороне ядра (BE1-03 / BE2), не публичным API.
3. `cancel` принимает текущую версию через `If-Match`, как и `delete`. Это не позволяет старой кнопке
   отменить draft после более новой правки. Повтор того же успешного cancel с исходной версией
   возвращает сохранённый cancelled-результат; другая устаревшая версия даёт 409.
4. Повтор `delete` на уже `deleted`: поведение согласовать отдельно; текущая реализация возвращает
   409 `INVALID_STATUS_TRANSITION`.

## Статусы (логика переходов)

| Из \ В | draft | confirmed | cancelled | deleted |
|---|---|---|---|---|
| draft | — | confirm | cancel | не через DELETE* |
| confirmed | нет | — | нет | DELETE (логическое) |
| cancelled | нет | нет | — | нет |
| deleted | нет | нет | нет | — |

\* Удаление черновика — через `cancel`, не через `DELETE` дневника.

- Только `confirmed` участвуют в аналитике и в `GET /entries` по умолчанию.
- `status=draft` — для экрана проверки; `cancelled`/`deleted` в список дневника не попадают.

## Null vs zero

- Неизвестное значение: JSON `null` (или отсутствие ключа только там, где схема допускает omit).
- Ноль — валидное измеренное/введённое значение (`0` шагов после уточнения допустим только если пользователь/источник явно сообщил 0; отрицательные шаги/длительность сна — **422**).
- Подтверждение (`confirm`) **не** меняет `field_origins.*.estimated` на «достоверное».
- Черновик `metrics` может не содержать `unit` и `local_date` либо содержать для них `null`, если распознавание не дало надёжного значения. Перед переходом в `confirmed` оба поля обязательны и не могут быть `null`.

## Питание и масса

- `nutrients_basis=per_100g`: значения `nutrients` относятся к 100 г. Итог порции равен значению, умноженному на `mass_g / 100`.
- `nutrients_basis=per_serving`: значения `nutrients` относятся ко всей сохранённой порции.
- `nutrients_basis=unknown`: автоматическое масштабирование запрещено до уточнения основы.
- При изменении `mass_g` для `per_100g` итог порции пересчитывается из неизменных значений на 100 г; нельзя повторно масштабировать уже рассчитанный итог.

## Границы календарного периода

- `list_confirmed_entries` принимает включительные календарные даты `from`/`to` и обязательный IANA `timezone` владельца.
- Реальный диапазон времени является полуоткрытым: от начала `from` включительно до начала дня после `to` исключительно в переданном часовом поясе. UTC-границы вычисляются после применения timezone, включая переходы летнего времени.

## Внутренние методы (не HTTP публичные)

См. `contracts/internal.yaml`: `create_draft`, `create_checkin`, `list_confirmed_entries` для BE2/BE3. Публичного `POST /entries` нет.
