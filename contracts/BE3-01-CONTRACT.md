# BE3-01 — схема контракта `/analytics`

**PROPOSED — ожидает формального review BE1 и FE2.**

## Совместимость с BE1 и FE2

### Общий OpenAPI

`contracts/openapi.yaml` содержит полный контракт BE1, а не отдельную урезанную копию BE3. Endpoint аналитики задан как `/analytics`, поскольку серверный префикс `/api/v1` задан в `servers`.

В `/analytics` используются параметры:

- `period`: обязательный enum `today | days_7 | days_21`;
- `timezone`: необязательный IANA timezone с default `Europe/Warsaw`;
- `checkin_category`: необязательная категория состояния, default `mood` описан в endpoint-контракте.

В YAML оставлен один корневой блок `components`, содержащий `securitySchemes`, `parameters` и `responses`. Ссылка на `#/components/responses/Unauthorized` поэтому разрешается в рамках общей структуры BE1.

### Entry и идентификаторы

Контракт использует правила BE1:

- учитываются только текущие записи со статусом `confirmed`;
- `draft`, `cancelled` и `deleted` не участвуют в расчётах, рядах и `sources`;
- идентификаторы `entry_id` и `id` в контрактных примерах имеют UUID-формат;
- источник содержит `entry_id`, тип записи и локальную дату для перехода к Entry;
- авторизация и ошибки остаются ответственностью общего BE1-контракта.

### Данные для FE2

Ответ содержит все элементы экрана из `feature/fe2-01-overview-contract`:

- карточки питания, количества приёмов пищи, сна, шагов, пульса и четырёх оценок;
- `observations.days_in_period` и `observations.days_with_any_data`;
- `observations.generated_at` как время актуальности snapshot;
- ряды `nutrition`, `sleep`, `steps` и `checkin`;
- выбор категории через `checkin.category` и query-параметр `checkin_category`.

Frontend не должен самостоятельно пересчитывать суммы, средние, выбор последнего дневного значения или фильтрацию статусов.

## Запрос периода и локальные даты

Период задаётся следующим образом:

```text
period=today | days_7 | days_21
```

Все границы периода являются локальными календарными датами в указанном IANA timezone. Сегодня включается в период:

- `today` — одна локальная дата;
- `days_7` — 7 локальных календарных дат, включая сегодня;
- `days_21` — 21 локальная календарная дата, включая сегодня.

В запросе timezone можно не передавать: тогда применяется `Europe/Warsaw`. Для однозначности FE2 рекомендуется передавать timezone явно. В ответе `period.timezone` обязателен и показывает фактически использованную зону.

`observations.generated_at` — UTC timestamp формирования snapshot ответа. Это не время последней исходной записи и не время, которое frontend должен вычислять самостоятельно.

## Карточки и значения `null`

### Питание

`cards.nutrition` содержит:

- `energy_kcal` — сумма записанных калорий;
- `protein_g`, `fat_g`, `carbs_g` — суммы Б/Ж/У в граммах;
- `incomplete` — true, если у включённого meal отсутствует хотя бы один нутриент;
- `meals_with_energy` — число meal с известной энергией.

Неизвестный нутриент не превращается в ноль. При полном отсутствии питания числовые итоги равны `null`, а не `0`; `meal_count.count` при этом равен реальному количеству подтверждённых meal.

### Количество приёмов пищи

`cards.meal_count.count` — количество подтверждённых meal в периоде. Ноль здесь означает, что подтверждённых meal действительно нет.

### Сон

`cards.sleep` содержит минуты сна, сумму, среднее и `days_with_data`. Сон относится к локальной дате пробуждения. Среднее считается только по дням, для которых есть данные; дни без данных не включаются в знаменатель.

### Шаги

`cards.steps` содержит количество шагов, среднее по дням с данными и число таких дней. Реальный ноль шагов не заменяется `null`; отсутствие измерения не заменяется нулём.

### Пульс

`cards.heart_rate` содержит последнее подтверждённое значение с `value_bpm`, фактическими `occurred_at`, `qualifier` и `entry_id`. Контекст не нормализуется искусственно: если Entry сообщает `instant`, в ответе остаётся `instant`; если `resting` — `resting`.

При отсутствии подтверждённого измерения `value_bpm`, `occurred_at`, `qualifier` и `entry_id` равны `null`.

### Оценки

`cards.checkins` содержит объект для каждой категории:

- `sleep_quality`;
- `digestion_comfort`;
- `wellbeing`;
- `mood`.

Каждый объект содержит `score`, локальную `date` и `entry_id`. При отсутствии оценки все три поля равны `null`. Это позволяет FE2 показать отсутствие данных и перейти к исходному Entry, не выполняя дополнительный поиск.

## Четыре ряда

### `series.nutrition`

Точка содержит `date`, `energy_kcal` и массив `source`, поскольку дневная сумма может состоять из нескольких meal. `energy_kcal: null` означает отсутствие подтверждённых данных питания за дату.

### `series.sleep`

Точка содержит:

```json
{
  "date": "2026-09-16",
  "value": 480,
  "unit": "min",
  "source": {
    "entry_id": "22222222-2222-4222-8222-222222222216",
    "type": "metrics",
    "local_date": "2026-09-16"
  }
}
```

`value: null` и `source: null` означают пропуск. Единица сна — минуты.

### `series.steps`

Точка содержит значение в `count` и источник выбранного дневного итога. Если за дату есть несколько актуальных дневных итогов, выбирается один по правилам раздела 7, а значения не суммируются.

### `series.checkin`

Ряд содержит выбранную категорию и точки со значениями `score_1_5`:

```json
{
  "category": "mood",
  "points": [
    {
      "date": "2026-09-19",
      "value": 4,
      "unit": "score_1_5",
      "source": {
        "entry_id": "22222222-2222-4222-8222-222222222221",
        "type": "checkin",
        "local_date": "2026-09-19"
      }
    }
  ]
}
```

Для пропуска `value` и `source` равны `null`.

## Правила отбора и расчёта

Зафиксированы следующие правила раздела 7:

1. В аналитику попадают только актуальные `confirmed` entries.
2. `draft`, `cancelled` и `deleted` исключаются.
3. Для повторных дневных итогов шагов и сна выбирается запись по `occurred_at`, затем по `updated_at`, затем по `id`.
4. Дневные итоги шагов не складываются между собой: для даты используется выбранное последнее актуальное значение.
5. Среднее считается по дням с данными, а не по всем календарным дням периода.
6. Сон измеряется в минутах и относится к дате пробуждения.
7. Пульс передаётся с фактическим контекстом исходного Entry.
8. Для каждой категории состояния выбирается последняя оценка за день; для карточки используется последняя доступная оценка за период.
9. Наличие, ноль и неполная сумма питания различаются явно через `null`, числовой ноль и `incomplete`.
10. Каждая непустая точка содержит источник для перехода к Entry; у пропуска источник равен `null` либо пустому массиву для nutrition.

## Синтетические входы и независимые ожидания

Входной набор находится в `analytics_input_records.json`. Это небольшой synthetic fixture, а не полный seed BE3-05.

Численные ожидания заданы независимо от будущей реализации расчётов:

- 165 ккал на 100 г при массе 200 г дают 330 ккал; при предыдущих 600 ккал сумма равна 930.
- После изменения массы той же записи на 150 г новая энергия равна 247,5 ккал; сумма равна 847,5.
- После logical delete изменённой записи остаётся 600 ккал; старая версия не учитывается повторно.
- Два дневных итога шагов 3000 в 12:00 и 5000 в 20:00 дают за дату 5000, а не 8000.
- Сон за две даты 420 и 480 минут даёт total 900, average 450 и `days_with_data = 2`.
- При отсутствии подтверждённых записей итоговые измерения и источники пусты или `null`; отсутствие не подменяется нулём.

## Проверки

`contracts/AnalyticsContractTest.java` проверяет в fixture-only режиме:

- чтение ожидаемых JSON;
- независимые численные ожидания 930, 900, 450, 5000 и 600;
- отличие `null` от нуля в пустом периоде;
- наличие всех ожидаемых snapshot-файлов;
- наличие навигационных источников в непустых данных.

Дополнительно перед review необходимо выполнить проектный валидатор Java 21/Gradle, например:

```bash
./gradlew validateContracts
```

или предусмотренную текущей сборкой команду модуля contract-validator:

```bash
./gradlew :contract-validator:validate --offline --console=plain
```

Фактический результат команды должен быть приложен к PR/отчёту с указанием проверенного commit. Наличие файлов без запуска валидатора не считается доказательством AC4.

## Непроверенное и блокировки

До завершения задачи остаются блокирующими:

1. человеческое подтверждение структуры `checkins`, точек рядов и источников от BE1 и FE2;
2. подтверждение, что версия `contracts/schemas/analytics.json` включена в общий контракт BE1;
3. запуск Java 21/Gradle-валидатора на текущем commit;
4. проверка fixture-клиента FE2 без frontend-пересчёта итогов;
5. реальная интеграция с endpoint и БД — она находится за границами BE3-01 и относится к последующим задачам.

Поэтому до выполнения этих действий задача не должна помечаться как полностью принятая, даже если файлы присутствуют и локальные assertions проходят.
