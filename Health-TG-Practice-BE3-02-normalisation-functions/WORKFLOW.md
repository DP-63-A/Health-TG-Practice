# Как использовать полные описания задач

Это предлагаемая организация работы поверх ТЗ. Она ещё не настроена в GitHub или Linear. Выбрать один основной трекер задач; хранить код, PR и code review в GitHub.

## До выдачи задачи исполнителю или агенту

1. Найти карточку по постоянному коду (например, BE1-03), а не создавать дубликат существующего Issue. Вставить полное описание. Проверить актуальные комментарии, чтобы сохранить уже согласованные решения коллег.
2. Назначить одного ответственного человека. Агент помогает ему, но не становится человеком, принимающим собственный результат. Назначить другого участника на review и определить принимающего.
3. Указать состояние, плановый срок и связь с вехой. Для задачи, проходящей через несколько вех, оставить полный объём и перечислить промежуточные результаты; не закрывать после ранней части.
4. Установить только действительные блокирующие связи по DEPENDENCIES.md. Уточнить в карточке: какой контракт/метод/результат нужен и что можно делать параллельно на согласованных fixtures.
5. Закрыть решения, блокирующие конкретный шаг, по DECISIONS.md. Человек/агент может продолжать независимые шаги, явно отмечая неустановленное.

## Связь Issue → ветка → PR → проверка

- Рекомендуемое имя ветки: `issue-<номер>-<код>-<краткое-название>`; это соглашение команды, а не требование Git. Ветка сама по себе не доказывает привязку к Issue.
- В PR явно поставить ссылку на Issue и повторить код задачи. Если команда хочет закрывать Issue автоматически после merge, использовать поддерживаемую GitHub связь/закрывающее ключевое слово только тогда, когда человеческая приёмка пройдена до merge. Иначе закрыть вручную после приёмки.
- Описать изменения и затронутые границы, дать таблицу AC → проверка → ожидаемое → фактическое → статус → доказательство, указать проверенный commit SHA. Приложить CI/тесты/сценарии, отметить fixture и live отдельно.
- Другой участник проверяет diff, критерии и доказательства. После исправлений повторить затронутые проверки; старый зелёный CI не подтверждает новую версию кода.
- Человек фиксирует решение о приёмке. Только после всех обязательных критериев и проверок задача получает Done. Сообщение агента и наличие PR сами по себе недостаточны.

## Замечания и следующая работа агента

Замечание к коду оставлять в PR у соответствующего места; замечание к требованиям/зависимости — в Issue. Указать ожидаемое и фактическое поведение, воспроизведение, критичность и необходимое доказательство исправления. Связанный дефект вне границ текущей задачи оформить отдельно с владельцем и зависимостью, не поручать скрыто переписать соседний модуль.

Перед исправлением агент должен получить актуальные комментарии через GitHub/API/инструмент либо явную передачу текста человеком. **`git pull` не загружает комментарии review и Issue в рабочие файлы.** После исправления ответить на замечание ссылкой на изменение и проверку; окончательное принятие оставляется проверяющему.

Повторяющееся замечание превратить в конкретное уточнение проектной инструкции, шаблона Issue или теста, если оно применимо шире одной строки. Не накапливать абстрактные запреты без воспроизводимой проверки.

## Рекомендуемые состояния

Backlog → Ready → In progress → Review → Accepted/Done. Блокировку отмечать отдельно с причиной и нужным результатом. Ready означает, что исполнитель понимает следующий доступный шаг; Done означает весь объём, все обязательные проверки и человеческую приёмку. Точные названия выбирает команда.

Ежедневная сверка по ТЗ: до 10 минут — что проверяемо сделано, следующий шаг, блокировка. Долгий автоматизированный цикл начинать после одного вручную пройденного цикла требования → Issue → код → проверки → review → приёмка.

## Перед переносом в Linear

В этом комплекте нет утверждения, что ссылки, milestone, зависимости или поля GitHub автоматически перенесутся. После выбранного способа импорта проверить их отдельно: 40 постоянных кодов, отсутствие дублей, полные тела, назначения, состояния, даты, связь с вехами и блокировки. Техническую поддержку переноса проверять по текущей документации выбранного импортера. Таблица DEPENDENCIES.md остаётся контрольным списком для восстановления связей.
