# Фото часов и скриншоты здоровья

Общий визуальный адаптер принимает еду, `health_screenshot` и `watch_photo`.
В работающем боте пользователь выбирает класс изображения перед обращением к модели.
Это позволяет выбрать часы на фотографии, где одновременно видна еда.
Одна попытка распознавания — один запрос; автоматических повторов нет.

## Диалог

1. Одно JPEG/PNG до 5 МиБ и 12 мегапикселей; альбом не поддерживается.
2. Выбор: еда, экран здоровья, часы.
3. Модель предлагает до трёх показателей, по одному каждого кода: `steps`,
   `sleep_duration_min`, `heart_rate`. Остальные подписи перечисляются как не импортированные.
4. До создания Entry бот уточняет неизвестное обязательное число, единицу и дату.
   Неизвестные время и квалификатор остаются `null`. Нельзя выводить шаги из
   подписи «Activity»/«Distance», а контекст «в покое» переносить с другого значения пульса.
5. Каждый показатель проходит общую карточку: проверить, исправить число/дату,
   сохранить или не сохранять. Можно пропустить показатель до создания черновика
   либо отменить оставшуюся очередь; уже подтверждённые записи сохраняются.
6. Следующий показатель предлагается после завершения текущего. Если запись завершена
   в Mini App, очередь продолжается на следующем сообщении, команде `/state` или callback в боте.

Дата показателя хранится в `payload.local_date`: день итога шагов, дата пробуждения
для сна, дата измерения пульса. Шапка телефона сама по себе не доказывает дату измерения.
`occurred_at` метрики — исходный Telegram `messageSentAt`, сохранённый до вызова модели;
время уточнения, повторного запуска и подтверждения его не заменяет.

## Контракт и происхождение

`response-schema.json` сохраняет прежний контракт еды. `metrics-response-schema.json`
описывает метрики; `visual-response-schema.json` объединяет обе ветки для live-провайдера.
Неизвестный/нечитаемый класс возвращает `unknown` и переводится в состояние ошибки.
Предлагаются повтор, ручной ввод или отмена с просьбой прислать читаемый фрагмент.
Ручной ввод сохраняет выбранный класс, спрашивает один показатель и обязательные поля.

Модель возвращает исходные числа/единицы и только `extracted` для известных полей.
`MetricCandidate` преобразует шаги в `count`, минуты/часы сна в `min`, пульс в `bpm`.
Для `7 h 20 min` передаются `value=7`, `unit=h`, `minutes_component=20`; код получает
440 минут, без приближения десятичными часами. Неизвестная единица требует уточнения.
Преобразованные поля имеют происхождение `computed`, пользовательские ответы —
`reported`. Исходные число/единица сохраняются в контексте диалога и кратко в
`source_ref.label` (до 256 символов); полным источником остаётся связанное изображение.
Подтверждение не меняет происхождение.

Если число сна неизвестно, нормализованная единица тоже остаётся неизвестной:
после числового ответа бот отдельно спрашивает часы или минуты. Например,
`7.5`, затем `ч` дают `450 min` с происхождением значения `computed`.
Исходное `null h` остаётся свидетельством модели. Старый незавершённый диалог,
который преждевременно сохранил `min`, также требует единицу пользовательского ответа.
Исправление уже созданной карточки сна принимает минуты и явно называет их.

Шаги должны быть целым числом от 0 до 1000000000: `1230.0` допустимо,
`1230.5` не округляется. Неверное предложение модели остаётся в исходном
свидетельстве и вызывает уточнение. То же правило действует при ручном вводе,
исправлении и записи через ядро/API. Сон и пульс могут быть дробными.

## Восстановление и файлы

Список кандидатов, текущий индекс и исходное время сообщения хранятся в DialogState.
При передаче в общую карточку очередь находится в `context.photo_queue`; исправления
карточки сохраняют её только для той же Entry. Одновременно существует один активный
черновик. Устаревшие кнопки не создают следующий показатель и не затирают чужой поток.

Каждая создаваемая Entry получает отдельную копию исходного изображения и отдельные
метаданные через существующий FileStorageService. Для одного изображения получается
до трёх копий, максимум 15 МиБ. Резервируемый UUID сохраняется до записи файла;
ключ создания Entry включает исходный update и индекс кандидата. Повтор после потери
подтверждения операции использует те же идентификаторы. Новый запрос к модели при
создании следующего показателя не выполняется. Не созданные/пропущенные кандидаты
не требуют файлов. Отмена использует сохранённый `reserved_file_id` для очистки
непривязанного файла даже после сбоя сохранения `file_id`. Намерение отмены
сохраняется до очистки; при сбое повтор продолжается после следующего обращения.
Связанные с Entry файлы сохраняются. Неопределённый результат сохранения Entry
также защищает файл; бот отличает эту ситуацию от удаления. В Mongo остаётся
техническая отметка отменённого UUID, запрещающая позднюю повторную загрузку.
Публичный HTTP API удаления не добавляется. Подробности — `docs/BE1-05-FILE-STORAGE.md`.

## Режимы

Существующая переменная `FOOD_RECOGNITION_MODE=disabled|fixture|live` управляет всеми
тремя классами; старую конфигурацию менять не нужно. Для live используются существующие
`GEMINI_API_KEY` и `GEMINI_MODEL`. Бот явно показывает выбранный режим.

В `fixture` еда использует прежний `fixture.json`, оба класса показателей —
`fixture-metrics.json` с соответствующим `image_class`. Это фиксированные учебные
ответы, не распознавание загруженной картинки и не доказательство качества модели.
Программные вызовы старого API еды остаются доступны; production включает
`FoodPhotoFlow.withImageClassSelection()`.

Автотесты не заменяют live-приёмку H01–H04/W01–W02: отдельно проверяются реальные
ответы модели, исходные картинки, исправление и подтверждение через Telegram/Mini App.
