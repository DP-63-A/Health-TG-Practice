# Выбор категории и оценки BE2-05

`org.healthtg.bot.checkin.CheckinSelector` — самостоятельная логика выбора без
БД, тестового хранилища и Telegram-транспорта. Она ещё не подключена к боту:
обычные `/state` и «Отметить состояние» сохраняют ответ о недоступности сценария.

## Использование

1. После проверки доступа вызвать `begin(owner, privateChatId, updateId)`:
   результат содержит четыре кнопки категорий.
2. Передать данные выбранной кнопки в `callback(owner, privateChatId, updateId, data)`:
   результат содержит пять кнопок оценки.
3. Передать выбранную оценку тем же методом: `Status.SELECTED` и
   `view().selection()` содержат неизменяемый результат выбора. Четвёртого
   подтверждения нет. Текст явно говорит, что данные не сохранены.

`owner` — Telegram ID, не UUID пользователя серверного API. `selectionId` —
идентификатор выбора, не ID сохранённой записи. Категория предоставляет `code()`
из `contracts/schemas/common.json`: `sleep_quality`, `digestion_comfort`,
`wellbeing`, `mood`; оценка соответствует диапазону `score` 1–5. Результат
не заменяет модель Entry и не содержит дату/статус сохранения.

## Повторы и границы

- `ACCEPTED` означает переход к категории или оценке, `SELECTED` — только первое
  завершение выбора. `REPLAY` возвращает текущий экран без нового события;
  `REJECTED` не меняет состояние. Только `SELECTED` предназначен для последующего
  вызова интеграционного слоя. Сам компонент не вызывает сохранение.
- Один активный выбор на пользователя. Новый `begin` с большим `updateId`
  заменяет предыдущий, и его кнопки становятся недействительными. Повтор
  исходного `begin` возвращает текущий экран без отката.
- Используются неотрицательные Telegram update ID. Переходы принимаются в
  возрастающем порядке в рамках активного выбора. Транспорт должен обрабатывать
  обновления последовательно, не параллельно менять их порядок. Telegram может
  сменить последовательность после долгого отсутствия обновлений: перед такой
  интеграцией потребуется политика времени жизни/сброса активного выбора.
- UUID в callback связан с владельцем и частным чатом. Чужие, некорректные,
  устаревшие кнопки и нарушенный порядок отклоняются. Allowlist остаётся
  обязанностью вызывающего обработчика: знание числового ID не является авторизацией.
- Первый выбранный балл фиксируется. Повтор той же оценки возвращает `REPLAY`,
  другая оценка после завершения отклоняется. Методы синхронизированы.
- Память ограничена 1000 активными выборами по умолчанию (лимит настраивается
  конструктором). При заполнении удаляется наиболее давно начатый выбор; его
  кнопки отклоняются. После перезапуска все прежние кнопки недействительны.
  Это кратковременная память интерфейса, а не хранилище медицинских записей.

В будущей интеграции нужны преобразование владельца, настоящее сохранение,
долговременная идемпотентность, обработка ошибок, время записи и отмена. Одна
гарантия `SELECTED` в памяти не обеспечивает exactly-once сохранение при сбое
или перезапуске. Эти операции остаются в полном BE2-05.

## Переиспользование

Из ранее написанных `CheckinDialogue`/`CheckinStore` ветки
`feature/be2-05-checkin` выделены подписи категорий, шкала, компактные callback
и последовательность выбора. Зависимость от store, fixture, cancel/retry
не перенесена. Это выделение существующей работы, а не параллельный полноценный
сценарий. При дальнейшей интеграции следует заменить соответствующую часть
старого `CheckinDialogue` этим компонентом, не оставлять два обработчика выбора.

Сборка и тесты в Windows (Java 21):

```powershell
.\gradlew.bat '-Dorg.gradle.jvmargs=-Dfile.encoding=COMPAT' :backend:bot:test :backend:bot:bootJar --offline --no-daemon --console=plain
```
