# Текстовый диалог (#7)

`CoreBotFlow` передаёт новый текст в `TextDialogFlow`, а созданный черновик — в
общий `DraftReviewFlow`. Обработчик использует сервисы ядра; прямых обращений к MongoDB нет.

- Распознанное событие создаёт DRAFT, а не подтверждённую запись.
- При неполных данных бот спрашивает конкретное недостающее поле: дату, единицу
  пульса или подтверждение дневного итога. Ответ заполняет поле; он не склеивается
  с исходным сообщением. При неоднозначном значении нужно отправить исправленное
  событие целиком. Кнопка «Ввести заново» явно переключает диалог на замену текста.
- Для нераспознанного текста бот предлагает заметку. Только «Создать заметку»
  разрешает подготовку её черновика. Отсутствующие календарная дата и время
  запрашиваются последовательно. Явные дата и время исходного текста используются
  без повторного вопроса. Текст заметки остаётся исходным, включая пробелы.
- «Отменить ввод» завершает диалог до создания Entry. После создания работают
  общие действия карточки: подтверждение, исправление, отмена, Mini App.

## Время и источник

У метрик `occurred_at` — момент исходного Telegram-сообщения, `payload.local_date` —
явная календарная дата показателя. Ответы на уточнения и часы обработки не заменяют
исходный момент. Если Telegram timestamp отсутствует, бот просит повторить ввод.
Для еды сохраняется прежнее правило: явная дата, а при отсутствии времени — время
обработки в часовом поясе пользователя. Для заметки обязательны дата и время от
пользователя; неоднозначное или несуществующее местное время при переводе часов
требует нового времени. `source_ref.telegram_update_id` указывает исходное сообщение.

## Восстановление и ограничения

До Entry сохраняются `text_note_offer`, `text_clarification`, `text_replace`,
исходный текст, timestamp, известные поля и причины уточнения. Новое сообщение не
заменяет предложение заметки, `/state` не сбрасывает незавершённый текстовый диалог.
Кнопки привязаны к владельцу через сохранённый диалог, исходному update и revision.
Старые кнопки не меняют состояние. Повтор принятого ответа не заполняет следующее поле.

Создание дедуплицируется ядром по update последнего ответа. При потере ответа
после записи бот восстанавливает активный черновик. Временная ошибка хранилища
сохраняет update в очереди; бот один раз сообщает о повторной обработке. Сбой
самого уведомления не подтверждает update и не останавливает повтор.

Каждое входное сообщение проверяется отдельно: максимум 2000 Unicode-кодовых точек,
кириллица и ё поддерживаются, emoji отклоняются по текущему ограничению MVP.
Повреждённый сохранённый контекст сбрасывается с просьбой повторить ввод.
Парсер ограничен грамматикой из [TEXT_INPUT.md](TEXT_INPUT.md); произвольный русский
текст не обещается распознавать как измерение.

Проверки сохранения/перезапуска/повторов с MongoDB находятся в `TextDialogStorageTest`,
маршрутизации — в `CoreBotFlowTest`, повторов транспорта — в `BotRuntimeTest`.
Они не заменяют ручную проверку Telegram/Mini App и интеграцию реального API аналитики.
