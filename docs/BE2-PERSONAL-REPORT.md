## Ключевые решения

| Решение | Причина | Цена |
|---|---|---|
| Значение попадает в дневник только после подтверждения: предложение → черновик → подтверждённая запись | Парсер и модель ошибаются; пользователь проверяет данные до сохранения | Дополнительный шаг |
| Быстрая отметка сразу подтверждена, защита — кнопка отмены | ТЗ требует три нажатия | Отмена выполняется логическим удалением |
| Неизвестное не заменяется нулём или текущей датой; бот спрашивает одно поле | Выдуманные значения искажают дневник и аналитику | Больше уточнений |
| Две даты: `occurred_at` (сообщение) и `local_date` (день показателя) | Сон и шаги относятся к дню, а не к моменту отправки | Сложнее модель данных |
| Ключ операции и revision в кнопках | Telegram может повторить update; старая кнопка не должна менять новую версию | Поддерживается один экземпляр бота |
| Детерминированный разбор текста без LLM | Обязательная LLM для текста запрещена; правила проверяемы | Узкая грамматика |
| Режим модели только явный, без скрытого fallback | Заранее записанный ответ нельзя выдавать за распознавание | Режим нужно настроить |
| `BigDecimal` для чисел | Точное десятичное значение | Многословная арифметика |

## Дефект, причина и регрессия

**Гонка двух черновиков оставляла файл закреплённым** (PR [#114](https://github.com/DP-63-A/Health-TG-Practice/pull/114), Issue #23).

Обнаружение: при анализе существующего кода перед реализацией. Review PR #114 содержал соседнее замечание о файле, который остаётся после отмены при сбое сохранения состояния диалога; описанная ниже гонка — отдельный сценарий.

- **Воспроизведение.** Два одновременных `createDraft` одного пользователя с разными изображениями. MongoDB допускает один активный черновик, поэтому второй запрос получает `ACTIVE_DRAFT_EXISTS` (или `EXISTING_UPDATE` для одинакового update), но его файл уже закреплён (`PINNED`). Очистка правильно не трогает закреплённые файлы, и лишнее изображение остаётся навсегда.
- **Red.** Новый тест на настоящей MongoDB с барьером перед сохранением, два варианта. Оба упали: ожидался `ACTIVE`, получен `PINNED`.
- **Причина.** Для проигравшего запроса не было компенсации.
- **Исправление.** `StoredFileLifecycle.pinForEntry` сообщает, был ли файл закреплён именно этим запросом (по прежнему состоянию документа). После подтверждённого конфликта `DefaultEntryCoreService.releaseRejectedFile` под блокировкой файла проверяет отсутствие ссылок из записей и освобождает только собственное новое закрепление. Ранее закреплённые файлы и сбои с неизвестным исходом остаются защищёнными.
- **Регрессия.** `FileLifecycleIntegrationTest`: оба конкурентных варианта и три защитных сценария (прежний `PINNED`, `entryId`, ссылка из старой записи). После исправления полный Java-прогон прошёл без ошибок и пропусков.
- **Ограничение.** После аварии процесса закрепление может остаться; общего сборщика потерянных файлов нет.

## Для защиты

- **Предложение → черновик → подтверждение.** Предложение (`RecognitionResult`, `TextParseResult`) не является записью; черновик хранится со статусом `DRAFT` и не попадает в аналитику; подтверждение — отдельное действие пользователя.
- **Повторы.** Ключ операции возвращает ранее созданную запись; revision в кнопке не даёт устаревшему действию изменить новую версию.
- **Даты и единицы.** День показателя отделён от времени сообщения; неизвестная дата или единица уточняется; сон хранится в минутах.
- **Небольшое изменение.** Уменьшить `ImageValidator.MAX_PIXELS` и показать, что граничный тест `ImageValidatorTest` (изображение 4000×3000) падает, затем вернуть значение.
